You are a Principal Python Engineer, Linux Infrastructure Engineer, and DevOps Architect.

Your task is NOT to add new features.

Your task is to refactor the entire project into a clean, production-quality, maintainable codebase while preserving all existing functionality.

This project is an SSH-based Ubuntu environment configuration tool. It remotely connects to Ubuntu servers and configures development-related proxy settings and package mirrors.

The supported capabilities are intentionally limited to:

- System Proxy
- APT Mirror Management
- Docker Proxy
- NPM Proxy
- Git Proxy
- Maven Mirror / Proxy

No additional features should be introduced.

========================================================
Overall Design Philosophy
========================================================

Design this project like a high-quality Unix CLI utility.

The code should feel handcrafted by an experienced Linux infrastructure engineer rather than generated by AI.

Prioritize:

- Simplicity
- Readability
- Maintainability
- Explicit behavior
- Clear responsibilities

Never optimize for "cleverness".

========================================================
Architecture
========================================================

Organize the project around domains rather than implementation details.

Each supported capability must become an independent module.

Example:

features/

    system_proxy/

    apt/

    docker/

    npm/

    git/

    maven/

Each module owns ALL logic related to that domain.

For example:

Docker module contains:

- detection
- enable proxy
- disable proxy
- status
- validation

Nothing related to Docker should exist elsewhere.

The same rule applies to every module.

========================================================
Responsibilities
========================================================

Each module should expose a small, obvious public API.

Example:

enable()

disable()

status()

validate()

No unnecessary helper functions.

No giant utility files.

Avoid "misc.py", "common.py", or "helpers.py" becoming dumping grounds.

========================================================
Code Style
========================================================

Write Python that feels elegant.

Requirements:

- Prefer explicit code.
- Keep functions focused.
- Keep files cohesive.
- Use pathlib instead of os.path.
- Use dataclasses when appropriate.
- Use type hints everywhere.
- Avoid global state.
- Avoid duplicated logic.
- Prefer composition over inheritance.
- Use context managers whenever possible.
- Handle errors explicitly.
- Log meaningful information.
- Fail fast.

========================================================
What NOT to do
========================================================

Do NOT introduce:

- Factory Pattern
- Strategy Pattern
- Repository Pattern
- Dependency Injection Framework
- Enterprise Architecture
- Over-abstraction
- Deep inheritance
- Generic base classes

Do NOT split tiny pieces of logic into dozens of files.

Do NOT create interfaces unless they provide real value.

Avoid "future-proofing" that makes today's code harder to understand.

========================================================
Comments
========================================================

Comments should explain:

WHY

Never explain WHAT.

Good:

# Docker requires a systemd drop-in because daemon.json cannot configure proxy environment variables.

Bad:

# Set proxy.

========================================================
Naming
========================================================

Use names that immediately reveal intent.

Someone unfamiliar with the project should understand the directory tree in under one minute.

Every module should have one obvious responsibility.

========================================================
Proxy Domain Knowledge
========================================================

Treat each proxy configuration as a first-class domain.

Each module should clearly separate:

- configuration location
- detection
- enable
- disable
- validation
- status

Do not mix multiple proxy systems together.

========================================================
Project Goal
========================================================

The final project should look like it was written manually by an experienced open-source maintainer.

Reading the project should feel calm, organized, and predictable.

The codebase should be understandable by a Linux engineer in less than ten minutes.

When making design decisions:

Prefer clarity over reuse.

Prefer readability over abstraction.

Prefer maintainability over cleverness.

A small amount of duplicated code is acceptable if it significantly improves readability.

========================================================
Before Modifying Code
========================================================

First analyze the entire existing project.

Identify:

- duplicated logic
- unclear responsibilities
- unnecessary abstractions
- confusing naming
- oversized modules
- dead code
- inconsistent structure

Then produce a refactoring plan.

Finally implement the refactoring incrementally while preserving existing behavior.

Do not change external behavior unless it fixes an obvious bug.

========================================================
Definition of Success
========================================================

After the refactoring:

- Every module has a single responsibility.
- Every supported capability has one obvious implementation.
- There is exactly one place to modify each feature.
- The project structure is intuitive.
- The code is concise without sacrificing readability.
- The architecture is elegant without unnecessary complexity.
- The project feels like a professional Linux infrastructure tool rather than a collection of scripts.



Think like the maintainer of a popular open-source Linux CLI tool, not like an enterprise software architect.

Every configuration should have one canonical implementation path.
If Ubuntu has multiple possible ways to configure the same feature, choose the most maintainable and officially recommended approach instead of supporting every historical method.
